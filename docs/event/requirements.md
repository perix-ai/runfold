# Event trajectory infrastructure requirements

> Language: English | [中文](requirements.zh.md)
>
> Document type: software requirements specification (SRS). This document
> defines what must be built and what qualifies as complete. See
> [`architecture.md`](architecture.md) for implementation principles and
> [`specification.md`](specification.md) for interfaces and data formats.
>
> Upstream baseline: DeepSeek Harness `0.1.2-alpha.3`, commit
> `dd6322d604e00eec1ba5e0c8541159906a21094a`.

## 1. Background

DeepSeek Harness (DSH) contains a proven Event-based agent trajectory
infrastructure: an append-only Session event log, JSONL persistence,
interruption repair, restore/fork semantics, and a Trajectory visualization UI.
Runfold extracts these capabilities for independent use by different agent
runtimes. The first real consumer, Nexent, runs in Python.

The project is therefore not a redesign inspired by DSH. It is a faithful
extraction of DSH's Event infrastructure, decoupled from the Harness host and
packaged as independently publishable, cross-language-equivalent components.

## 2. Terminology

| Term | Definition |
| --- | --- |
| Event | A persistent fact in an agent execution trajectory, with a contiguous sequence number and timestamp |
| Session | An ordered collection of Events and its lifecycle, consisting of one header and a zero-based contiguous Event sequence |
| Trajectory | A projection and UI derived from Event/Session data; it is a derived view, not a separate data facility alongside Event |
| restore | Read and validate a persisted Session, repairing it under DSH rules when necessary |
| resume | Continue appending Events after restore while preserving sequence, lifecycle, and persistence continuity |
| fork | Create a new Session with lineage from a valid stable prefix |
| surface | The Event subsequence that forms the model-visible conversation (currently `user/message`, `assistant/message`, and `tool/result`) |
| repair | Deterministically close unfinished turns, steps, and tool calls left by an abnormal interruption |

Here, resume does not mean reconnecting a frontend stream. It does not promise
to restore a process stack, an in-flight tool call, or an arbitrary code
instruction pointer. Closure and repair after interruption follow the DSH Event
implementation. `fork` is behavior, not an independent top-level facility;
similarly, the existence of the word `stream` does not justify a peer
implementation directory alongside Event.

## 3. Goals

The final result must satisfy all of the following:

- R-G1 Preserve DSH source, directory relationships, and behavior in the
  TypeScript implementation wherever possible;
- R-G2 Ensure the standalone implementation and its published artifacts do not
  depend on the DSH runtime, package namespace, or complete Harness;
- R-G3 Provide a native, complete Python Event implementation rather than an
  SDK that calls TypeScript;
- R-G4 Make TypeScript and Python obey the same logical contract and read and
  write each other's trajectory data;
- R-G5 Preserve the behavior and quality of the DSH Trajectory UI and render
  trajectories generated by either language.

## 4. Scope

### 4.1 Capabilities to preserve or extract

- Core models including Session, Event, header, sequence, time, and lineage;
- Append-only mutation, immutable snapshots, and derived surface/trajectory
  projections;
- Existing persistence formats such as JSONL, including reading, appending,
  restart, and corruption repair;
- Restore, resume, fork, and DSH interruption-repair behavior;
- DSH Trajectory projection, conversation assembly, React UI, styling, and
  localization;
- TypeScript and Python SDKs, implementations, tests, and cross-language
  conformance verification.

### 4.2 Explicitly out of scope

- A general Event Bus, message broker, or complete agent runtime;
- A server, Node sidecar, or process service added so Python can call
  TypeScript;
- The Harness plugin system, model calls, tool execution, sandbox, or control
  plane;
- An adapter-system design;
- A separate State-based trajectory design;
- A Python frontend UI;
- Long-term memory, knowledge bases, model routing, skills and MCP
  registration, or a product-level control plane, all of which belong to other
  runtimes or application layers.

## 5. Stakeholders and use cases

### 5.1 Nexent, the first Python consumer

Nexent must be able to install the Python Event package directly, record
trajectories in its own process, and perform restore, resume, and fork without
deploying a Node server or managing a TypeScript subprocess. Nexent's existing
frontend stream-reconnection concept must remain distinct from Event resume.

The Nexent integration must not introduce a dedicated format. It must use the
same schema and conformance contract as the TypeScript implementation so the
existing Trajectory UI can also read its trajectories.

### 5.2 TypeScript consumers

Consumers create, append, persist, restore, and fork Sessions in-process through
`@runfold/event`. They render an Event history in any React page through
`@runfold/trajectory-ui`. The UI depends only on `@runfold/event` and public
third-party packages.

## 6. Quality requirements

- Behavior: all retained DSH upstream regression tests continue to pass against
  the extracted implementation. The current gate comprises 626 Event and
  persistence cases, 182 UI-runtime cases, and 94 Trajectory cases.
- Interoperability: a persisted trajectory written by either implementation can
  be restored, appended to, and forked by the other. Normalized headers, Events,
  surfaces, messages, and repair results are field-for-field equal.
- Dependencies: published artifacts require no DSH package, and public APIs and
  types expose no DSH namespace.
- Auditability: every deviation from upstream records its source, rationale, and
  regression protection.

## 7. Acceptance criteria

The Event extraction is production-ready only when all of the following are
true:

- A1 The DSH behavioral baseline and Trajectory UI quality have not regressed;
- A2 TypeScript and Python both have complete native implementations and full
  tests;
- A3 Both languages pass the same conformance suite and operate on persisted
  trajectories in both directions through their public restore APIs;
- A4 Published artifacts contain no DSH runtime dependency or public namespace
  leak;
- A5 Nexent can record, restore, resume, and fork using only the Python package;
- A6 Every necessary deviation has source documentation, rationale, and a
  regression test.

See [`tasks.md`](tasks.md) for progress and acceptance status.
